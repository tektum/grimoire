# Proof: the conversion worker pool

Measured on a development machine with `node test/pool/measure.mjs 200` (after `bun run build`) in `packages/adapters/markdown-milkdown`, Node 26.8.2, a 32-core shared machine (load average about 4, so read the figures as indicative). The Markdown is generated by `src/testing/generate.ts`; "cap" is 0.9 MB of prose Markdown, a 1,502,629-byte state (the state cap was 1,536,000 bytes when this was measured; it is 1,000,000 bytes now, decision 162).

## What the pool is

A guard, not a speed-up. `createMarkdownConverter(options)` implements the `MarkdownConverter` port over a `piscina` pool of 2 worker threads by default that runs `convertInProcess` / `seedInProcess` unchanged. Limits and where they come from:

| Setting | Value | Source |
|---|---|---|
| `poolSize` | 2 (`GRIMOIRE_CONVERT_POOL_SIZE`; about 90 MB of memory per worker, measured as process memory) | design |
| `timeoutMs` | 10,000 for state to Markdown (queue wait plus run, one `AbortSignal.timeout` created at call); the server passes `GRIMOIRE_SAVE_TIMEOUT_MS` | design |
| `seedTimeoutMs` | 10,000 for Markdown to a page (`GRIMOIRE_SEED_TIMEOUT_MS`; 5,000 when this was measured), same rules; the result says "the Markdown took too long to convert" | design |
| `reseedTimeoutMs` | 30,000 for a rebuild from stored Markdown (`GRIMOIRE_RESEED_TIMEOUT_MS`) | design |
| `heapMb` | 512 (`resourceLimits.maxOldGenerationSizeMb`) | design |
| `queueLimit` | 32 calls waiting | **not in the design**: chosen here. At about 1 to 2 s per cap-sized page and a 10 s timeout, at most about 5 queued calls could finish anyway; 32 refuses a flood at once and keeps small pages queueing |
| `closeDeadlineMs` | 5,000 in the adapter; the server passes 1,500 from its shutdown budget (`apps/server/src/lifecycle/budget.ts`) | design |

## Failure mapping

| Event | Result |
|---|---|
| timeout (running) | `timeout`; piscina terminates the running worker and starts a replacement |
| timeout (still queued) | `timeout`; the call is removed from the queue and no worker is touched |
| `ERR_WORKER_OUT_OF_MEMORY` | `out-of-memory`; worker replaced |
| queue full | `internal`, detail `queue-full`, at once |
| a second seed from a key that has one running | `internal`, detail `one-at-a-time`, at once, not queued; `seed` needs a non-empty key (the page's id from the server), else `internal` / `no-key` |
| worker throws / exits / answers nonsense | `internal`, detail `worker-failed` / `worker-exited` / `worker-bad-reply` |
| call after or during `close()` | `internal`, detail `closed` |
| converter's own failures | passed through unchanged |

Details are fixed sentences; no error message is copied (an error could carry page text). piscina's own `maxQueue` does not count a task that carries an `AbortSignal` (every call does), so the limit is enforced by a counter in the adapter; piscina's `maxQueue` is also set.

## Numbers

| Page | State bytes | In process (median ms) | Pool (median ms) | Overhead (ms) |
|---|---|---|---|---|
| 10 KB | 53,278 | 39.7 | 43.3 | 3.5 |
| 100 KB | 540,948 | 429.3 | 442.9 | 13.6 |
| cap (1,536,000 at the time; now 1,000,000) | 1,502,629 | 926.7 | 1010.2 | 83.5 |

The overhead is the state copy (the caller keeps its bytes, so a copy is moved), the structured clone of the Markdown and text back, and scheduling. It is small against the conversion itself.

Cold start: a new pool answers its first 10 KB conversion in 201 ms (worker boot, module load, headless context), against 55 ms for the second call. The worker thread is started when the converter is created.

Main-thread event loop during a cap-sized conversion: through the pool the longest gap between 10 ms timer ticks is 10.6 ms (`monitorEventLoopDelay` max 10.2 ms, i.e. the timer resolution); the same conversion in process blocks the loop for 937.7 ms. Test `test/pool/event-loop.test.ts` asserts that the median `GET /ping` answers within 100 ms and that the maximum ping and the maximum loop delay each stay under 500 ms during the cap-sized conversion (measured there: 13 ms and 11 ms; written to `test-results/m2/pool-1mb.json`).

200 out-of-memory conversions (fixture worker, `heapMb: 64`): 200 of 200 returned `out-of-memory` in 12.6 s (63 ms each, including the replacement worker); the main process heap used was 18.8 MB before and 18.2 MB after (RSS 651 MB before and 221 MB after: it fell, it did not grow), the pool still served afterwards and `stats().threads` was 0 after `close()`.

## Worker file

Built to `dist/worker.js`. The sources import each other with `.js` specifiers that Node cannot resolve to `.ts`, so a worker cannot start from `src`: `defaultWorkerPath()` gives `./worker.js` next to the built `pool.js`, and `../dist/worker.js` when the module is the source (the test runner). The pool tests call `tsc -b` first (`test/pool/support.ts`). `test/pool/built.test.ts` runs `test/pool/built-check.mjs` in a plain `node` process against `dist`.

## Transfer

The design says the adapter passes a copy with a `transferList`; this is what is built, so the caller's buffer is not detached (it is written to the database after the call). The copy is made with `new Uint8Array(state)`, which also copes with a view into a larger buffer and with a `Buffer` (its `slice()` shares memory). A seeded state comes back moved (`piscina.move`).
