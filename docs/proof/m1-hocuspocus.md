# Proof note: Hocuspocus as the collaboration host

Versions: `@hocuspocus/server` and `@hocuspocus/provider` 4.8.0, crossws 0.4.17, `rate-limiter-flexible` 11.5.0, Node v26.13.1 (`docs/proof/m1-port-finding.md`, `docs/proof/m1-limits-findings.md`).

Decision: stay

Hocuspocus stays the collaboration host (R2.44). No requirement named below ended as `fail`; the rows that differ from the spec text say so and point to the numbered differences below, and R4.36 is `not tested` because it needs a real proxy (a deployment check). The fallbacks of R2.44 (the `y-websocket` server, or our own server on the Yjs protocol libraries) were not built.

## How to re-run

- `make up && make test-m1` runs the ten scenarios, each in its own process, against the Compose stack and writes `test-results/m1/<name>.json` (git-ignored; `status` is `pass` or `fail`). `make test-m1-office` runs the 100-user office scenario and writes `test-results/m1-office/office.json`. `make test-m1-mutation` raises each limit and expects its scenario to fail (`Makefile`).
- `bun run test:integration` runs the package and server integration tests cited below (they need `make db-up` or `make up`).

## Differences between the spec text and what Hocuspocus 4.8.0 does

1. **The provider reports close code 1000 for server CLOSE messages.** A refusal reaches the provider as `authenticationFailed({reason})` and the close as 1000; raw sockets see the real code (4400, 4401, 4403, 4404, 4413, 4429, 4503, 4500 and the shutdown 1001). Provider-side tests therefore assert on the reason or the stateless message. Touches R4.11, R4.15, R4.16, R4.17.
2. **Hocuspocus does not close the socket on a rejected authentication.** `peers.ts` closes it 250 ms after a refusal unless a document on that socket has connected or is admitted and still opening (a live reservation); the check repeats every 250 ms, so a socket that holds nothing is closed in the end. Touches R4.3, R4.11.
3. **The throttle extension is not used.** `rate-limiter-flexible`, keyed by the address our own upgrade handler takes from the trusted-proxy setting, replaces it, because the source reading found `@hocuspocus/extension-throttle` trusts client forwarding headers and puts every client without a header in one bucket. An earlier recommendation to use the extension is overturned. **The count is of attempts that do not authenticate**: the first design counted every upgrade, and in the office scenario 250 of 300 sockets were locked out for 5 minutes and 90 of 100 reconnects after a restart were refused; after the change all 300 synced (about 3.3 s) and all 100 reconnects synced (about 1.1 s) (`docs/proof/m1-presence-findings.md`, "Office scenarios"). A bad Origin is a 403 and is not counted; at most 10 sockets per address may be unauthenticated at once (429, `Retry-After: 2`, not counted); an unauthenticated socket is destroyed after the pre-authentication timeout (`GRIMOIRE_COLLAB_PREAUTH_TIMEOUT_SECONDS`, default 5 s). Touches R4.19, R12.28.
4. **`onUpgrade` does not exist with our wiring.** Hocuspocus is attached to the shared HTTP server through our own `upgrade` listener, so the Origin check and the per-address limit live in `packages/adapters/collab-hocuspocus/src/upgrade-guard.ts` and run before Hocuspocus sees the request (`docs/proof/m1-presence-findings.md`; `docs/proof/m1-port-finding.md`). Touches R12.15, R4.19.
5. **A failed store is not retried by Hocuspocus; it only logs.** Retry with backoff (1,000 ms doubling to 30,000 ms), the alarm after 5 consecutive failures (`collab.store_alarm`, once per streak) and the abandon at the shutdown deadline are ours. Touches R4.24, R4.25.
6. **`beforeHandleMessage` closes only the document connection, and the state cap is not there.** Every throw closes the document connection (default code 4205) and leaves the socket open, so the message limit closes the socket itself with 4429. The cap and the validation are in `beforeSync`, which receives the parsed sync type; there a throw also closes the document connection, so `malformed-update` closes with 4422 and `state-cap` with 4423 (4423 is our choice) (`docs/proof/m1-limits-findings.md`). Touches R4.16, R4.17, R4.18.
7. **`maxPayload` is a crossws option; the server sees 1006, not 1009.** The client gets 1009; on the server the only trace is a `RangeError: Max payload size exceeded` error call, which our bridge turns into `collab.limit_hit` (limit `message-size`) (`docs/proof/m1-limits-findings.md`). Touches R4.16.
8. **The state cap counts the real result.** An update is refused when the page's state after it would pass the cap (1,000,000 bytes by default), measured on a copy; "current size plus update size" would stop a page at the cap from ever shrinking (`docs/proof/m1-limits-findings.md`, "Decisions"). Touches R4.16.
9. **`onDisconnect` has no `connection`, only a socket id,** so presence bindings are kept per document as `Map<clientId, socketId>` and `Map<socketId, clientId>` (`docs/proof/m1-presence-findings.md`). Touches R4.12.
10. **One database pool (R2.21) is not literally true.** `apps/server/src/composition.ts` builds three pools: the API pool (the library default, 10 connections), the page store's own pool (maximum 4, with `statement_timeout` and `query_timeout` from `GRIMOIRE_COLLAB_STORE_TIMEOUT_MS`, default 2,000 ms) and a sign-in lookup pool (maximum 4, with its own short timeout); the last two exist only when the process serves collaboration. A hung database therefore cannot block the other pools. Touches R2.21.
11. **Two message budgets.** Counting every frame closed a client typing 15 characters a second (about 30 messages a second with cursor movement, 290 to 298 per 10 s) about every 10 s, and an ordinary mouse (60 presence updates a second) every 5.5 s. **The budget of R4.18 now applies to document messages (300 per 10 s per user and page); presence messages over their own budget (3 per 100 ms per socket, about 30 a second) are dropped, never a reason to close,** and the newest dropped update is replayed when the window ends (a 20 s drag at 60 a second ends at the final position within 200 ms). The budget is keyed by user and page, so reconnecting does not renew it, and a reconnect may draw 5,000 messages in its first 6 s once per 60 s (a provider sends every offline edit as its own message) (`docs/proof/m1-limits-findings.md`, "Two budgets" and "Reconnect backlog"). Touches R4.18.
12. **A client could stop the server by resetting a refused upgrade.** After Node emits `upgrade` it no longer listens for socket errors on that socket, so a client that reset the connection while the server was writing a refusal (404, 400, 429 or 503) caused an uncaught exception that ended the process, and an unauthenticated client needed no credentials for it. Fixed: an `error` listener is attached to the socket after `upgrade` (`packages/adapters/collab-hocuspocus/src/host.ts`, `upgrade-guard.ts`). Pinned by `apps/server/test/collab/upgrade-reset.test.ts`, "a rejected upgrade whose client resets the connection is never an uncaught exception".

## Known limits

Stated plainly; none is hidden by a passing scenario.

1. **The `restart` scenario would not catch a server that lost data which clients re-upload.** It checks what the surviving clients hold and that the database then matches; a server that lost a page and was refilled by the clients' re-sync would pass. This is the same mechanism as the stale-tab merge of R4.33; the page epoch handshake addresses the page-level case. R4.30.
2. **Stopping the `store-failure` scenario with Ctrl-C can leave the database grant revoked.** The scenario restores the privilege when it finishes or fails, but a hard stop in the middle can leave `UPDATE` revoked on `pages` for the runtime role. The next run refuses to start in that state and prints the fix: `grant update on pages to grimoire_app`. R4.24, R13.5.
3. **`apps/server/test-e2e` is type-checked by `bun run typecheck` (`tsc -b`) and by `make test-m1`, but its scenarios do not run in `bun run test`** (the `unit` project); they need the Compose stack.
4. **`make down-volumes` deletes the local data volumes** (`down -v --remove-orphans`); so does `make reset`. `make down` keeps them. Database initialisation scripts run only on an empty volume, which is why a volume created before the roles changed needs `make down-volumes`.
5. **Compose passes only some `GRIMOIRE_*` settings to the container.** `make check-compose` fails when a setting the loader knows is neither passed nor listed as deliberately not passed; a setting that is not passed takes its default in the container (an example of the kind of setting that matters behind a proxy: `GRIMOIRE_TRUSTED_PROXY`, which Compose does pass through, empty by default).
6. **Short database outages raise no alarm.** `collab.store_alarm` fires after 5 consecutive failed saves of a page, once per streak; failures below that are logged as `collab.store_failed` only, and a save that succeeds in between resets the count.
7. **Presence names and colours are client-written** (R3.16, R14.11): the server guarantees only `user.id`; a user can show a false display name or colour for their own cursor (`docs/proof/m1-presence-findings.md`).
8. **Throttles are per process, in memory.** A restart resets every limiter and ban, and one container is assumed (R4.35); behind a proxy the address is right only when `GRIMOIRE_TRUSTED_PROXY` is set (Compose passes it through from the host environment; it is empty by default).
9. **A client id is not an identity.** The server binds the one client id a socket writes with on its first document update, and a collaborator with write access who writes with another participant's client id before that participant's first update takes the binding: the other participant's presence is dropped for as long as the squatter's socket stays open (its binding is removed when that socket closes, and the other participant's next presence update is accepted then; reconnecting does not help while the squatter stays), and the attacker's cursor is shown under that client id, still labelled with the attacker's own verified user. Nothing in the editing protocol can prevent this (a writer can already create operations under any client id), so the server guarantees the user label of each connection, not the client id. Stored authorship and who is shown as editing are not affected.
