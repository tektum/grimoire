# findings: limits on the collaboration host

Measured on Hocuspocus 4.8.0, crossws 0.4.17 (vendored `ws`), `rate-limiter-flexible` 11.5.0. Code: `packages/adapters/collab-hocuspocus/src/extensions/limits.ts`. Tests: `packages/adapters/collab-hocuspocus/test/limits/` (boundaries with fakes, real sockets) and `apps/server/test/collab/limits*.int.test.ts` (real built server, real database, `GRIMOIRE_COLLAB_*` variables through `loadConfig`).

## Hooks

| Hook or option | Result | What was found |
|---|---|---|
| `onConnect` (priority 800, after the name check of auth at 1000, before `onAuthenticate`) | works | Runs once per document, before any verifier or database work. Checks in order: process total, page total, then (page not open yet) open documents and memory. A thrown `Refusal` reaches the client as `authenticationFailed({reason})`; the host closes the socket 250 ms later. The page and process counts are only a cheap first check here; they are raised, and decided again, when the document arrives (the end of the auth extension's `onAuthenticate`, before the client is told it is authenticated), so connections arriving at the same instant cannot overshoot them (tests: `apps/server/test/collab/review-claims.int.test.ts`, `packages/adapters/collab-hocuspocus/test/limits/limits.test.ts`). |
| `connected` | works | Count of connections per page and in total (keyed by socket id, so a repeated call counts once). An editor joining a page already past the warning point receives `state-warning` here. |
| `onDisconnect` | works | Fires once per document connection with `clientsCount` after removal. Frees the counts, drops the socket's rate counter, and starts the idle timer when the page has no connection left. |
| `beforeHandleMessage` | differs | Every throw closes only the document connection (code and reason taken from the error, default 4205); the socket stays open. So the rate limit closes the socket itself, `connection.webSocket.close(4429, 'rate-limited')`, after sending the stateless refusal, then throws to drop the frame. It only sees the raw frame, so the state cap and the validation are not here (next row). |
| `beforeSync` | differs | The specification puts the state cap in `beforeHandleMessage`; it is here because this hook receives the parsed sync type and the update bytes (no hand-written varint parsing). Validation: `Y.decodeStateVector` for type 0, `Y.decodeUpdate` for types 1 and 2, anything else is malformed. A throw closes that document connection: there is no way to refuse one message and keep the connection, so `malformed-update` closes with 4422 and `state-cap` with 4423 (the specification gives `state-cap` no code; 4423 is our choice, kept in `SESSION_CLOSE_CODES`). The provider reports the server CLOSE as code 1000, so provider tests assert on the stateless message. |
| `beforeHandleAwareness` (limits, priority 800, before presence at 600) | works | Presence over its budget is dropped by emptying `states` and `removedClients`: Hocuspocus then applies and broadcasts an empty update, which changes nothing and reaches nobody. The raw frame is read in `beforeHandleMessage` (the awareness hook has only the decoded maps) and kept per connection so the newest dropped update can be replayed with `connection.handleMessage` when the window ends. |
| `afterUnloadDocument`, `onDestroy` | works | Clear the idle timers. |
| `maxPayload` (crossws `serverOptions`, set in `host.ts`) | differs | A frame over the limit closes the socket with 1009 on the client, exactly as the specification says. On the server, crossws's `close` hook reports it as 1006, not 1009, and the only trace is an `error` hook call whose message is `RangeError: Max payload size exceeded`; the bridge matches that text to log `collab.limit_hit` (limit `message-size`). A frame of exactly 1,048,576 bytes is accepted. |

## Choices the specification left open

- **State cap: the real result counts.** An update is refused when the page's state after applying it (measured on a copy) would pass the cap. The cheap path adds the update size to a running estimate (which only errs high); the exact size is computed only when the estimate says the cap could be crossed. The specification said "current size plus update size"; with that rule a page exactly at the cap could never shrink, because a deleting update is also bytes. Nothing is stored for a refused update: the hook runs before the update is applied.
- **Warning:** `state-warning` goes once per loaded page to every connected editor when the state first passes 80% of the cap, and once to each editor who joins later while it is past it.
- **Two budgets (revised after measuring real use).** The first design counted every frame: 300 per 10 s per socket. Measured on the real server, typing at 15 characters a second with cursor movement sends one document update and one presence update per keystroke, about 30 messages a second (290 to 298 per 10 s), and was closed with 4429 about every 10 s; dragging a selection at 30 presence updates a second tripped it too, and an ordinary mouse (60 a second) every 5.5 s. Now:
  - **Document messages** (everything that is not awareness): the spec's 300 per 10 s (R4.18), counted per user and page once the user is known (so reconnecting on a new socket does not renew it) and per socket before that, refused with `rate-limited` and 4429. Typing 15 characters a second is 150 per 10 s, a margin of 2.
  - **Presence** (awareness, type 1; a query-awareness frame, type 3, is not a presence update: it counts against the document budget above and the per-user byte budget, and is kept out of the reconnect allowance): 3 per 100 ms per socket, about 30 a second, named constants `PRESENCE_POINTS` and `PRESENCE_WINDOW_SECONDS` in `limits.ts` (there is no setting for it, so no variable was added). Over budget an update is dropped, not relayed, never closes; the newest dropped update is replayed when the window ends, so the last cursor position arrives at most about 100 ms late (measured: a 20 s drag at 60 a second ends at the final position within 200 ms). One `collab.limit_hit` with limit `presence-rate` per socket per 10 s.
  - **Message type** is read from the frame header: a varint name length, the name, then the type byte; no decoding of the rest (`messageType` in `limits.ts`).
  - Both budgets use `RateLimiterMemory`.
- **Several tabs of one user.** Measured: three browser tabs of one user typing on the same page at 10 characters a second each sit exactly at the shared document budget (300 per 10 s), and one tab was closed once in 30 seconds (nothing lost: the edits stay in the tab's document and the next sync sends them). The budget was not changed. The web client should use one connection per page per browser profile where it can (for example one shared worker), or back off and resync quietly on a rate-limit close (4429).
- **Log volume.** `collab.upgrade_refused`, `collab.refused`, `collab.limit_hit`, `collab.auth_unavailable` and `collab.state_warning` can be triggered again and again by a client without credentials or by a flooder, so `log-throttle.ts` logs the first occurrence of each kind per 10 s window at once and one `collab.log_suppressed` line (fields `suppressedEvent`, `variant`, `count`, `windowSeconds`) at the end of the window; the kind is the reason, code, limit or page id, never an address. At most 1,000 kinds are tracked at once; beyond that occurrences are only counted, into one overflow line per window. Alarm-class events (`collab.store_*`) are never throttled. `collab.connected` is throttled by a burst: the first 10 per 10 s window are logged and the rest are counted into the `collab.log_suppressed` line, so counting `collab.connected` lines undercounts a reconnect storm.
- **Reconnect backlog and who may use it.** A Hocuspocus provider queues every edit made offline as its own message (one per edit, not merged) and sends them all when its first server message arrives, which is after the server has set the connection up: it is NOT in Hocuspocus's pre-authentication queue (a 5,000-edit backlog passes with that queue at its default of 1,000 messages). Rule, in `limits.ts`:
  - The document budget is keyed by user and page (not by socket), so reconnecting does not renew it.
  - In the first 6 seconds of a document connection (counted from the first message handled) document messages draw from an allowance of 5,000 messages per user and page, which refills 60 seconds after it was first drawn on (`rate-limiter-flexible`, key user and page). 5,000 is a very long offline session at one message per edit. When the allowance or the 6 s is used up, the normal budget applies. 6 s because the server handles about 1,500 messages a second, so 5,000 needs 3.3 s.
  - Worst case for an authenticated attacker on one page: 5,000 per 60 s from the allowance (83 a second) plus the budget of 300 per 10 s (30 a second): about 113 messages a second, under 4 times the normal 30. The first burst is not stopped by the budget (a flood starting right after authentication gets the 5,000 once per minute); the state cap and the frame limit still bound what is stored and relayed per message.
  - A close with 4429 loses nothing: the provider clears its message queue when it flushes it, but the edits stay in its document and the next sync exchange sends them as one merged update. Tests: reconnect after 500 and 5,000 offline edits passes; an attacker reconnecting every 3 s for 60 s gets at most 5,000 + 7 x 300 through.
  - Unauthenticated sockets: Hocuspocus's queue of frames sent before authentication is capped at 1 MiB (`maxUnauthenticatedQueueSize` in `host.ts`; the library default is 5 MiB) and 1,000 messages (the library default); over the cap the socket is terminated. A raw socket sending 64 KB frames without authenticating is closed after about 17 frames and the server grows by less than 64 MiB.
  - Presence replay: the replayed frame goes through `connection.handleMessage`, so the presence extension (ownership, `user.id`) checks it again (a forged state held by the budget is dropped and the sender gets `presence-violation`); a frame held for a socket that has closed is discarded.
- **Rate limit key:** user and page once the user is known (so a new socket does not start fresh: closing and reconnecting does not renew the budget), the socket id otherwise. Two tabs of one user on one page share a budget; the tests use different users for different clients.
- **Idle unload:** Hocuspocus already unloads a page right after the last save (measured: under 1 s after the last client leaves, store call made first). That satisfies "no later than the idle time". `GRIMOIRE_COLLAB_IDLE_UNLOAD_SECONDS` therefore only drives a safety net: a page that is still loaded with no connection that long after the last one left is unloaded (`unloadDocument` itself refuses while a save is pending). Tested with a stand-in extension that refuses the unloads for 1.5 s: unloaded at 2 s, not at 1 s. It cannot be observed through the built server, where Hocuspocus unloads first.
- **Per-user limits** were added after this measurement: `GRIMOIRE_COLLAB_MAX_SOCKETS_PER_USER` (default 20), `GRIMOIRE_COLLAB_MAX_DOCUMENTS_PER_USER` (default 50) and `GRIMOIRE_COLLAB_BYTES_PER_SECOND_PER_USER` (default 2,097,152); they are not measured here.

## Effect on the specification

The 300 messages per 10 seconds of R4.18 applies to document messages. Presence messages are rate-limited by dropping (about 30 a second per socket), not by closing.

## Numbers

Round trip of 1,000 small edits (client A types one character, client B must see it before the next), five runs each, limits extension registered versus removed from the registry: about 0.137 ms per edit against 0.133 ms. The hooks cost about 1 to 3 microseconds per message in isolation. Note: at the default 300 messages per 10 s a client that sends faster than 30 messages per second is rate limited by design; the measurement lifts the rate for that reason.
